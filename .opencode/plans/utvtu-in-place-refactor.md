# UTvTU 原位重构方向草案

日期：2026-10-11。状态：定位与总体路线已确认；模块设计、实施顺序为待评审建议，本轮未修改产品代码。

## 1. 已确认的方向

- 定位：**人声制作工作站**，覆盖歌声编辑、合成、混音与交付的完整流程。
- 方式：在现有 UTvTU 上渐进重构，上游 OpenUTAU 作为设计与行为参考。
- 平台：当前仅验证 Windows，不扩展移动端或其它桌面平台。
- 产品原则：歌声制作是中心；混音与交付服务于这条工作流。通用 DAW 功能按实际需求逐项评估。
- 前端需要重新梳理信息架构、交互状态、模块职责和样式归属。界面重构应落实这些边界。

## 3. 上游如何作为参考

| 上游已核查的实现 | UTvTU 可借鉴的原则 | 采用前必须验证的差异 |
|---|---|---|
| `Pipeline/Identities.cs`、`Pipeline/Snapshots.cs` | 工程修订号、修改影响范围、后台使用快照 | 编辑、撤销和实时调参是否都能生成一致的修订；快照是否覆盖所需输入 |
| `Pipeline/PhraseSourceBuilder.cs` | 后台构建乐句，旧请求退出时不能覆盖新结果 | 取消、工程切换、歌手释放、缓存失效 |

| `Render/RenderView.cs` | 渲染结果通过只读投影更新界面，并合并通知 | 当前仍依赖 PlaybackManager 单例，这一耦合应单独处理 |
| `RenderEngine.RenderMixdown` 的 planner 参数 | 导出使用独立计划器，避免污染播放状态 | 播放与导出结果、节拍器、范围导出和插件状态 |
| 独立 `OpenUtau.UiTest` 工程 | 进程级应用初始化与其它测试隔离 | UTvTU 当前测试宿主、全局状态和真机验收方式 |

上游也保留了 DocManager、DocumentSnapshotStore、RenderView 等单例。评价标准应是边界是否明确、
行为是否正确、生命周期是否完整、能否独立验证；具体实现按这四点取舍。

## 4. 目标职责与依赖

先确立逻辑边界，按实际需要拆程序集，避免一次新增大量空工程。

| 模块 | 负责 | 应通过明确接口交接的工作 |
|---|---|---|
| 应用壳与工作区宿主 | 窗口、视图导航、面板布局、分离与收回 | 保存、导出、工程编辑、音频设备选择 |
| 前端功能模块 | 编排、歌声编辑、混音、素材库、偏好设置的交互与呈现 | 共享工程修改、后台作业、插件资源管理 |
| 应用操作与工程会话 | 命令路由、工程修改、撤销、脏状态、作业调度、会话关闭 | 窗口控件、DSP、文件格式编码 |
| 工程数据与文件服务 | 项目数据、兼容读写、保存结果、恢复与迁移 | 实时插件实例、播放状态、视图布局 |
| 合成与缓存 | 音素化、乐句构建、合成器适配、缓存、失效与结果发布 | 用户导航、实时混音参数、输出设备 |
| 音频与插件运行时 | 运输控制、信号链、效果、输出、导出消费、插件生命周期 | UI 控件和实时读取可变工程对象 |

目标调用关系：视图 → 功能 ViewModel → 应用操作/会话 → 数据或运行服务。
组合入口负责创建实例和连接接口；回调、订阅、计时器、任务及原生资源必须有明确拥有者。

过渡期可由适配器封装现有 DocManager、PlaybackManager 和 RenderEngine。
每次替换一个调用入口并迁移全部调用者，验收后删除被替代路径，防止永久形成两套状态来源。

## 5. 建议实施顺序

### 阶段 0：最小回归保障与边界清单

核对当前基线能否构建、运行；测试数字取实际输出。选择固定工程覆盖保存、重开、撤销、
歌手切换、试听、导出和 VST 状态恢复。回滚前修复过的高风险问题先复现，确认必要性后单独修复。
产品功能、缺陷修复、依赖升级和结构调整分别提交。

### 阶段 1：主窗口职责与前端命令

这是建议的首批架构工作。现有 `CommandDefinition` 直接持有 `Action<MainWindow>`，
主窗口同时处理文件流程、快捷键、视图生命周期和编辑交互。

先选“打开工程、保存、关闭确认”这一条完整工作流，提取可独立验证的应用操作；
窗口只提供文件选择和确认交互，命令从显式上下文获取操作服务。
再独立整理工作区宿主和分离/收回生命周期，复用已有 ViewSwitcher 策略。
职责拆分与视觉修改分批进行，用户可分别判断行为和界面变化。

验收：菜单与快捷键行为一致；失败或取消保存时关闭行为正确；视图反复分离/收回响应正常；
相关逻辑可以使用替身交互验证，不依赖构造完整 MainWindow。

### 阶段 2：工程修改与保存一致性

建立统一的修改事务及修订记录。拖动类操作可逐次发布实时参数，结束时合并为一次撤销记录；
混音修改的影响范围应避免不必要的歌声重渲染。VST 原生 GUI 参数能否可靠进入撤销需要单独验证。

保存针对一个明确修订：收集状态 → 序列化 → 临时文件写入 → 原子替换 → 成功后更新保存点。
保存期间又产生修改时，应仍显示未保存。失败、自动保存、纯净格式导出和正常保存分别定义结果。
旧 `.ustxp` 工程通过兼容入口验证，用户数据目录仍保留 `OpenUtau Plus`。

### 阶段 3：合成、播放、导出与资源生命周期

在现有 RenderEngine 门面基础上逐项评估上游快照、乐句构建和音频块发布机制。
一次只替换一种机制，保留明确的行为对照；处理 Waited 时间语义以及 VST 销毁安全点的差异。
工程关闭必须能取消并等待后台任务，释放订阅、计时器和原生资源；视图重挂拥有不同的生命周期。

验收：旧任务不能回写新工程；试听与导出时序及效果正确；音频回调不执行文件 IO 或模型推理；
插件增删、seek、停止、工程切换和同时导出的资源访问安全。

### 阶段 4：前端体验与样式逐模块重构

按照完整人声制作流程重新组织界面，逐模块处理状态、交互、可访问性、样式归属和编译绑定。
几何与令牌以用户交付 HTML 为准，图像用于观感参考；既有设计是否继续采用需在设计评审中明确。
每个模块由用户实机预览后再进入下一批。测试优先验证实际呈现与行为，保留必要的设计源一致性契约。

## 6. 第一批评审与验收要求

- 先评审“主窗口的工程文件操作边界”：谁决定保存、谁提供对话、谁记录保存结果、谁决定关闭。
- 任务写明目标文件、依赖、行为约束、替换入口和验收方式；同一文件只有一个写入者。
- 每完成一个通过验收的步骤立即中文原子提交。阶段结果可预览、可回退，避免积累长期 WIP。
- 工程往返、音频时序、撤销、失败保存和资源释放必须用行为证据验证。
- 重构进度以职责迁移和旧路径删除衡量，新增文件数和代码行数不作为目标。
